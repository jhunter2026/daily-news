# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal daily-news workflow tool (not yet audience-facing — see "Product direction" below): it pulls headlines from a fixed list of RSS/Atom feeds (local news + outdoor/hunting/conservation sites), uses Gemini to score each headline on "breakout potential," "policy relevance," and "urgency," stores everything in Supabase, and emails a daily brief via Resend. The homepage (`app/page.js`) renders every stored headline scoring above `SCORE_THRESHOLD` (`lib/curation.js`), ranked by a blend of breakout and urgency — it reads only from Supabase, it does not fetch feeds live.

## Product direction

This is currently an operator tool, not a public product — the owner uses it to build a daily posting workflow (manually posting to Instagram/X using `/social`'s generated images/captions). Scores are intentionally never shown to any public-facing surface (captions, images) — only the owner sees them, on the homepage/email/dashboard. `app/dashboard/page.js` is a first, view-only step toward a real operator tool (see that route's entry below) — no actions yet (mark posted/skip, manual scan trigger) by design, added incrementally. Eventually a public-facing product (a website, a Substack, or an owned email list — shape undecided). Keep this context in mind when making design calls: don't assume the current homepage's public-style masthead design is a public product design; it's just what a personal-use view looks like today.

## Commands

- `npm run dev` — start the Next.js dev server
- `npm run build` — production build
- `npm run start` — run the production build
- No test suite, linter, or type checker is configured.

## Architecture

- **Next.js 14 App Router**, plain JS (no TypeScript). Routes:
  - `app/page.js` — server component homepage. Reads every `headlines` row scoring above `SCORE_THRESHOLD` and published within `RECENCY_WINDOW_HOURS` (`lib/curation.js`), ranked by a blend of `score` and `urgency_score` (ties broken by recency). No per-source cap.
  - `app/social/page.js` — manual-posting workflow: same curated list as the homepage, but each story renders as a downloadable `/api/story-image` thumbnail plus (when present) a copyable Instagram caption (`app/social/CopyCaptionButton.js`, a small client component for `navigator.clipboard`). No auto-posting to Instagram/X — this just prepares images/captions for the user to post themselves.
  - `app/dashboard/page.js` + `app/dashboard/DashboardTable.js` — the operator dashboard, v1 (view-only, no actions yet — see "Product direction" above). Unlike every other view, this reads `getRecentHeadlines()` (not `getCuratedHeadlines()`): every story in a **7-day** window (`DASHBOARD_WINDOW_DAYS`, deliberately longer than the 48h the public views use — see `lib/curation.js`) regardless of score, including ones that failed to score entirely (shown with a "scoring failed" tag, detected the same way as elsewhere — `summary` starting with `ERROR`), so the owner can see what the AI passed on or choked on, not just the curated picks. Grouped into day sections (Today/Yesterday/Aug N — computed in `DASHBOARD_TIMEZONE`, `America/Los_Angeles`, so a late-evening story doesn't misleadingly land in "tomorrow"'s group by UTC's clock), each independently sortable by clicking its column headers; a source filter applies across all groups at once. The page (server component) fetches once; `DashboardTable` (`'use client'`) handles all sorting/filtering/grouping client-side against that already-fetched data — no re-fetching per interaction. No auth gate (matches the homepage/`/social`; nothing here is more sensitive than what those already show, and there are no actions yet to protect).
  - `app/api/story-image/route.js` — `GET ?id=<row id>` renders that one headline as a 1080x1080 (Instagram-square) PNG via `next/og`'s `ImageResponse`. Runs on the **Edge runtime** (`export const runtime = 'edge'`), not the Node runtime the other routes use — image rendering doesn't need Supabase writes or long-running loops, and Edge sidesteps the Hobby-plan 10s Node function ceiling entirely. Reads via the public anon client (same data the homepage already shows; no auth needed). Two things worth knowing:
    - **Fonts**: Satori has no default bold variant, so `fontWeight: 700/800` silently renders as regular unless real weighted font data is supplied. Fetches Inter (400 + 800) per request via Google Fonts' text-subsetted `css2` endpoint, which returns a truetype/opentype `src` Satori can parse (a normal browser request gets woff2, which it can't).
    - **Content**: only ever renders `title`/`score`/`policy_relevance`/`urgency_score`/`source` (as badges) — never `summary` (that's an internal editorial note for the owner's email digest, not public-facing) and never `caption` (that's meant for Instagram's caption field, not baked into the image). If `image_url` is present, it's used as a full-bleed background with a bottom gradient scrim and white text; otherwise falls back to a plain white card with dark text.
  - `app/api/scan/route.js` — the fetch-and-score pipeline. Runs **several times a day**, not once — triggered externally by `.github/workflows/scan.yml` (GitHub Actions, currently 6x/day at 15:00/17:00/19:00/21:00/23:00/01:00 UTC — chosen to land on roughly 8am-6pm Pacific every 2 hours; see that file's comments for the DST caveat) hitting `GET /api/scan`, since Vercel Cron only fires a given schedule once a day on the Hobby plan and that's not frequent enough to catch breaking news within the day. This was originally attempted at every 20 minutes, but GitHub's scheduler silently throttled that down to roughly hourly in practice — a known GitHub Actions limitation for sub-hourly schedules, not a config mistake; every-2-hours is comfortably above wherever that throttling threshold is and fires reliably. Gated by `CRON_SECRET` (optional — checked against an `Authorization: Bearer` header or `?secret=` query param; unset means the endpoint is open) — the GitHub Actions workflow reads the same secret from a **repo secret** of the same name (Settings → Secrets and variables → Actions), which must be kept in sync with Vercel's env var manually (no automatic link between the two). Deployed on Vercel's **Hobby plan, hard 10s function ceiling** (`maxDuration = 10`, cannot be raised without upgrading) — the whole handler is deadline-driven, not count-driven, because Gemini call latency (not a fixed item count) is what actually determines how much fits:
    1. Fetches + parses every feed in `lib/feeds.js` **concurrently** (`Promise.all`) with `rss-parser` (custom User-Agent header — several of these feeds block default UA strings; `customFields` also pulls in `media:thumbnail`/`media:content`, which aren't part of the base RSS spec rss-parser handles by default). This has to be concurrent, not sequential — 9 external feeds fetched one at a time can burn the entire 10s budget on network latency alone before a single headline gets scored. The scoring loop that follows processes feeds in an order rotated daily (`rotateFeeds()`, based on day-of-epoch mod feed count) rather than `lib/feeds.js`'s fixed order — otherwise sources near the end of that list would starve every time earlier ones filled the whole scoring budget; now that this runs several times a day, every feed also gets multiple chances within the same day regardless of rotation position. `extractImageUrl()` pulls each item's photo (checked in order: `<enclosure>`, `media:thumbnail`, `media:content`, then a last-resort regex for the first `<img>` in the embedded article HTML) for `/api/story-image`'s background — about 2/3 of feeds have one (Outdoor Life, Field & Stream, Outside Online, NPR, The Free Press, MeatEater); Gothamist/LAist/BHA don't, and get the plain-card fallback instead. Returns `null`, not an error, when nothing matches.
    2. For each feed's newest 10 items, skips any link already scored in Supabase (checks `score`/`policy_relevance` are non-null) and, for `category: 'general'` feeds, skips anything `isRelevant()` (`lib/relevance.js`) rules out as off-topic — those are never stored. Remaining candidates are scored with `scoreHeadline()` (`lib/scoring.js`) and upserted one at a time (immediately, not batched at the end) until `SCORING_DEADLINE_MS` is hit, at which point any unprocessed feeds/items are marked `skipped`/`partial` in the response rather than attempted. Even on a busy day, most new headlines across all 9 feeds still won't get scored in a single run — they get picked up on a later scan run (within a couple hours, not a full day) if still in that feed's latest-10, or need `/api/backfill` once they age out.
    3. Upserts scored rows into Supabase's `headlines` table on conflict `link` (so `link` is the dedup key across runs).
    4. Returns a JSON summary (`ranAt`, `elapsedMs`, per-feed `results` with `scored`/`pending`/`errors`) — useful for manually curling the endpoint to debug a run.
  - `app/api/cron/route.js` — the once-a-day email brief. Triggered on a schedule (see `vercel.json`: daily at 13:00 UTC) via Vercel Cron hitting `GET /api/cron` — this is the one route Vercel's own scheduler still drives directly, since a daily digest is exactly the once-a-day cadence Vercel Cron is built for. Same `CRON_SECRET` gate as `/api/scan`. Does no RSS fetching or Gemini calls at all — just reads whatever `/api/scan` has already written via `getCuratedHeadlines()` and emails it through Resend. Kept deliberately thin (one DB read, one email send) specifically so it has nothing left to time out on.
  - `app/api/backfill/route.js` — a few one-off maintenance modes, gated by the same `CRON_SECRET` as the cron route (shared, not a separate secret):
    - default (no query param): backfills rows that predate a newly-added scoring field (currently: rows with `policy_relevance IS NULL`). Same 10s ceiling and deadline-driven design as the cron route (`TIME_BUDGET_MS`) — realistically only a handful of rows get scored per call, so clearing any real backlog means calling this many times in a loop until the response's `remaining` hits 0. For each row it applies the same `isRelevant()` check as the cron route (looking up the row's feed category by `source`): irrelevant general-source rows are deleted rather than backfilled, everything else gets scored and updated in place.
    - `?stats=1` — read-only: table-wide `total` row count, `nullCount` (rows still missing `policy_relevance`), and the actual `nullRows`. No writes, no Gemini calls.
    - `?cleanupRelevance=1` — one-off: `isRelevant()` only gates a `general`-source headline *before* it's first scored, so rows scored before the filter existed (or before a keyword-list update) never get re-checked and can linger in the digest/homepage indefinitely even though they're off-topic. This re-applies `isRelevant()` to every already-scored general-source row and deletes the ones that fail. No Gemini calls, so it's a single pass over the whole table rather than a time-budgeted loop.
- **`lib/feeds.js`** — the single source of truth for which feeds are pulled. Each entry has `url`, `source` (used as the display name and Supabase key), and `category` (`general` / `outdoor` / `policy`). `category` drives the relevance filter: only `general` feeds are filtered, since `outdoor`/`policy` sources are on-topic by definition.
- **`lib/relevance.js`** — `isRelevant(title, category)`: keyword heuristic (no API call) that gates whether a `general`-category headline is worth scoring at all. Tune `OUTDOOR_KEYWORDS` to adjust what counts as on-topic.
- **`lib/curation.js`** — `SCORE_THRESHOLD` (currently 5) and `RECENCY_WINDOW_HOURS` (currently 48, for the curated/public views) plus `getCuratedHeadlines(client)`, `getRecentHeadlines(client)` (dashboard-only, `DASHBOARD_WINDOW_DAYS` = 7), and `scoreColor(score)` (the color banding: red 8+, orange 7s, amber 6s). `getCuratedHeadlines` (score > threshold, blended rank, 48h window) backs `app/page.js`, `app/social/page.js`, and the cron route's email digest; `getRecentHeadlines` (no score gate, plain `pub_date` order, 7-day window) backs the dashboard only — deliberately a separate function with its own window rather than a parameter on the curated one, since "everything unranked over a week" and "the good stuff, ranked, over 48h" are different enough queries (and different enough *purposes* — monitoring vs. curation) that forcing one function to do both would need a boolean flag threading through every call site. `scoreColor` is shared by the homepage and `app/api/story-image/route.js`. One shared implementation instead of quietly-drifting copies. The 48h recency window (curated views only) exists because without one, a high-scoring story from weeks ago would rank ahead of anything newer forever, since nothing ever aged it out — filtered on `pub_date` (real-world publish time), not when the pipeline happened to score it, since the goal is surfacing what's actually current. The threshold gate (`score > SCORE_THRESHOLD`) stays on raw breakout score only; ranking among qualifying stories is a blend of `score` and `urgency_score` (`rankScore()`, private to the module) computed and sorted in JS after the fetch, since Supabase's query builder can't `.order()` by an arithmetic combination of two columns without a generated column or RPC. Falls back to pure breakout for rows scored before `urgency_score` existed, rather than treating a missing value as 0.
- **`lib/scoring.js`** — `scoreHeadline(title)`: the shared Gemini call, used by both the cron and backfill routes. One prompt, one call, asks for strict JSON (`breakout_score`, `policy_relevance`, `urgency_score`, `summary`, `caption`) and parses it. `urgency_score` is judged independently of `breakout_score` — a slow-burn analysis piece can have huge breakout potential but low urgency, and a minor-but-literally-breaking development can be the reverse; conflating the two was why the site felt like it wasn't surfacing breaking news even after the recency window fix. `summary` and `caption` are deliberately different in purpose and the prompt says so explicitly: `summary` is an internal editorial note ("this scores high because...") for the owner's email digest and can reference all three scores directly; `caption` is public-facing, written for Instagram, and is told never to mention any scoring dimension. On any failure it returns `score`/`urgency_score`: null (and `caption: null`) and puts the error message in `summary` (prefixed `ERROR:`) rather than throwing — the UI filters out summaries starting with `ERROR`. Both routes check for this explicitly (`policy_relevance === null` / `summary` starting with `ERROR`) and report it as `scoreFailed`, distinct from a real `scored` success — a write can fully succeed while still carrying a failed score, and that row needs to be picked up again later (it stays matched by backfill's `policy_relevance IS NULL` query). Also exports `GEMINI_TIMEOUT_MS`: the SDK has no built-in call timeout, so `scoreHeadline()` races the Gemini call against this to turn a slow/stuck request into a normal caught error instead of riding out to a hard Vercel function timeout. Callers' own deadlines (`SCORING_DEADLINE_MS`, `TIME_BUDGET_MS`) must stay sized around this — their between-items check means the real worst case is *their own deadline + one more full `GEMINI_TIMEOUT_MS`*, not the deadline alone.
- **`lib/supabaseClient.js`** — anon-key Supabase client, used only by the public read path (`app/page.js`). Reads `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_KEY`.
- **`lib/supabaseAdmin.js`** — service-role Supabase client (`SUPABASE_SERVICE_ROLE_KEY`, not `NEXT_PUBLIC_`-prefixed — never bundled to the browser), used by the cron and backfill routes for every read/write. This bypasses RLS entirely and exists because the anon key's RLS policy on this table turned out to allow `UPDATE` but silently deny `DELETE` (a `.delete()` would return no error yet affect 0 rows) — discovered when `/api/backfill`'s `remaining` count wouldn't move despite rows genuinely getting scored. Don't switch these routes back to the anon client without re-checking that policy.
- **Supabase `headlines` table** (schema inferred from usage, not defined in-repo): columns include `id`, `title`, `link` (unique/conflict key), `source`, `pub_date`, `score`, `policy_relevance`, `urgency_score` (nullable integer, populated by both scan and backfill), `summary`, `image_url` (nullable text, only populated by the scan route on ingest — `/api/backfill` re-scores old rows but can't retroactively recover an image, since it only has the DB row, not the original RSS item), `caption` (nullable text, populated by both scan and backfill since it only needs the title).
- Required env vars: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`, `GEMINI_API_KEY`. Optional: `CRON_SECRET` (strongly recommended — see below). The GitHub Actions workflow additionally needs a **repo secret** (not a Vercel env var) of the same name and value, set separately in GitHub (Settings → Secrets and variables → Actions) — the two `CRON_SECRET`s live in different systems and don't sync automatically.

## Notes for making changes

- To add/remove a feed, edit `lib/feeds.js` only.
- To change what counts as "good enough to show" (threshold, ranking, or color bands), edit `lib/curation.js` — the homepage, `/social`, the email digest, and the story-image generator all read from it, so there's nothing else to keep in sync.
- Neither the scan route nor the backfill route requires auth unless `CRON_SECRET` is set. Both run with the service-role key (full read/write/delete, bypassing RLS), so an unset `CRON_SECRET` means anyone with either URL can burn Gemini quota, or delete rows via `?cleanupRelevance=1` — set it. The (much lighter) cron route uses the same gate mostly for consistency, since all it does is read+email.
- All three of scan/cron/backfill set `export const maxDuration = 10` to match the Vercel Hobby plan's hard ceiling. If you upgrade plans, raise this and the `*_DEADLINE_MS`/`TIME_BUDGET_MS` constants in scan/backfill together — they're deliberately kept a couple seconds under `maxDuration` for response/query overhead, not set to match it exactly.
- If you change how often `/api/scan` should run, edit the cron expression in `.github/workflows/scan.yml`, not anything in `vercel.json` (that file only controls the once-a-day `/api/cron` email trigger).
